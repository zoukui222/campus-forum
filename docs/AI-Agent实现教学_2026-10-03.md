## 第 1 章 先分清四个词

| 词 | 是什么 | 在本项目里的体现 |
|---|---|---|
| LLM | 会说话的函数，输入文本输出文本 | DeepSeek `deepseek-chat` |
| Prompt | 你塞给模型的话 | `AiAgentService.buildSystemPrompt()` |
| Function Calling | 让模型**说出**它想调用哪个函数、参数是什么 | `tools` 声明 + 响应里的 `tool_calls` |
| Agent | 把「模型说要调」变成「真的调了、结果再喂回去」的**循环** | `AiAgentService.run()` 的 for 循环 |

**必须记死的一句话**（面试九成会追问）：

> 模型自己不执行任何东西。它只是输出一段结构化文本说「我要调 `search_posts`，参数是 `{"keyword":"考试"}`」，
> 真正去查数据库的是**我的 Java 代码**。模型的价值在于它自己决定**调哪个、传什么参**——
> 这是它和关键词搜索的本质区别。

## 第 2 章 一次对话到底发生了什么

### 2.1 真实报文（本机抓的原始 SSE，未做任何过滤）

问「论坛里有哪些和考试相关的帖子？」：

```
event:meta
data:{"chatLogId":1,"model":"deepseek-chat","tools":["list_boards","create_post","get_forum_stats","get_post_detail","search_posts","top_post"]}

event:tool_call
data:{"name":"search_posts","arguments":"{\"keyword\": \"考试\", \"limit\": 10}"}

event:tool_result
data:{"name":"search_posts","success":true,"durationMs":8,"preview":"检索到 1 篇帖子：\n- id=15 《免费领考试资料啦》 板块:考试资料 作者:管理员 浏览:2 回复:0 [已置顶]\n"}

event:content
data:{"text":"考"}

...（后面几百行，每个字一个 content 事件）...

event:done
data:{"iterations":1,"promptTokens":2714,"completionTokens":124,"durationMs":1632,"chatLogId":1}
```

### 2.2 六种事件

| 事件 | 谁产生 | 前端拿它做什么 |
|---|---|---|
| `meta` | 后端开场 | 显示可用工具数、记录会话 ID |
| `tool_call` | 后端（模型决定的） | 立刻显示「正在检索帖子…」 |
| `tool_result` | 后端（工具执行完） | 改成「已检索帖子（8ms）」 |
| `content` | 后端（模型吐字） | 追加到气泡，形成打字机效果 |
| `done` | 后端收尾 | 显示「1 次工具调用 · 1632ms · tokens」 |
| `error` | 后端兜底 | 在气泡里显示失败原因 |

### 2.3 完整链路

```
浏览器 fetch GET /api/ai/chat?message=...   (Authorization: Bearer <token>)
        │
        ▼
① AiAgentController.chat()        ← 请求线程，这里取身份快照
        ▼
② aiAgentExecutor 线程池           ← 换线程，ThreadLocal 失效
        ▼
③ AiAgentService.run()
        │  ★ 重建 SecurityContext（见 3.1）
        │  写 ai_chat_log(RUNNING) 拿主键
        └──► for (round < 5)
                 ├─ DeepSeekClient.chatStream(messages, tools)
                 ├─ 有 tool_calls → ToolRegistry.invoke() → 审计 → 结果塞回 messages → 下一轮
                 └─ 没有 → 正文流式推前端 → break
        ▼
④ 回填 ai_chat_log + done 事件 + 清理 SecurityContext
```

## 第 3 章 三个难点（面试主战场）

### 3.1 `SecurityContextHolder` 跨线程失效 —— 这个项目最值钱的一处

**问题**：`SecurityUtils.getUserId()` 底层是 `SecurityContextHolder`，默认 `MODE_THREADLOCAL`。
Agent 换线程后，Agent 线程里 `getAuthentication()` 是 **null**，
于是 `SecurityUtils.getUserId()` 抛 `BusinessException(401)`。

关键在于：**这个项目里不止 AI 模块用它**。`@RequireAdmin` 切面、`ScoreAspect`（积分切面）
全都通过 `SecurityUtils` 取当前用户——`ScoreAspect` 里还专门写了注释：
「因为 AOP 是在同一个线程里执行的，SecurityContextHolder 依然有效」。
作者清楚这个前提，而 SSE 恰恰把它打破了。

**两种解法，以及为什么选第二种**（这段最能体现工程判断）：

| 解法 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 显式传参 | 把身份封装成 `AgentContext` 一路传下去，工具只用它，不碰 ThreadLocal | 简单直接、无隐式状态 | **下游 service 无法复用**：凡是内部调 `SecurityUtils` 的既有代码，要么改造要么绕开 |
| **重建 (本项采用)** | 在 Agent 线程里 `SecurityContextHolder.getContext().setAuthentication(...)` | 下游代码**完全无感**，一行既有代码都不用改 | 必须记得 `finally` 里 `clearContext()`，否则线程池复用会污染下一个请求 |

```java
// AiAgentService.bindSecurityContext()
UsernamePasswordAuthenticationToken authentication = new UsernamePasswordAuthenticationToken(
        context.getUserId(), null,
        Collections.singletonList(new SimpleGrantedAuthority("ROLE_" + role)));  // 前缀必须是 ROLE_
SecurityContextHolder.getContext().setAuthentication(authentication);

// …执行工具…

finally {
    SecurityContextHolder.clearContext();   // 必须清理！
}
```

**⚠️ 一个必须答上来的追问：「那你为什么还留着 `AgentContext`？」**

> 两者分工不同。`AgentContext` 管「模型**能不能看到**某个工具」——它是纯数据对象，
> 用来在 `buildToolSpec()` 里按角色裁剪工具声明，不依赖任何线程状态。
> `SecurityContext` 管「下游代码**能不能取到**当前用户」——它是给既有 service / 切面用的。
> 前者是给模型的，后者是给框架的，缺一不可。

**验证证据**：发帖实测中数据库落库 `user_id=8`（提问者 lzt 的 id）。
如果身份丢了，这个字段要么是 null，要么会抛 401 直接失败。

### 3.2 流式 function calling 的 `arguments` 是分片到达的

第一片：`{"index":0,"id":"call_abc","function":{"name":"search_posts","arguments":"{\"key"}}`
第二片：`{"index":0,"function":{"arguments":"word\":\"考试\"}"}}` ← **没有 id、没有 name**

必须按 `index` 聚合（`Map<Integer, AiToolCall>`）并把 `arguments` 片段拼接（`Map<Integer, StringBuilder>`），
拼完才是合法 JSON。不聚合就是随机的 JSON 解析失败。见 `DeepSeekClient.parseSse()`。

### 3.3 三级角色下的工具权限双重管控

- **声明层**：`buildToolSpec()` 对 USER 角色**不下发** `top_post`——模型根本不知道它存在，
  从源头避免注定失败的调用；
- **执行层**：`invoke()` 里再校验一次，防绕过。

实测：MODERATOR 6 个工具、USER 5 个。

**为什么不在声明层就让它调用失败？** 因为模型看到「有个置顶工具」就会在用户要求时兴冲冲地调，
然后收到「无权限」再回头解释——浪费 token，体验差，还可能让用户误以为「有权限但失败了」。

## 第 4 章 和博客论坛那套比，差在哪（重要）

你两个项目都接了 Agent，面试官几乎一定会问「有什么区别」。这张表就是答案：

| 维度 | 博客论坛 | 校园论坛 | 说明 |
|---|---|---|---|
| 框架 | Spring Boot 2.5.9（javax） | **Spring Boot 3.3.5（jakarta）** | 包名从 `javax.*` 换成 `jakarta.*`，代码全部重写 |
| Java | source 1.8 | **17** | 后者能用 `java.net.http.HttpClient` + `BodyHandlers.ofLines()` 读流；前者只能 `HttpURLConnection` 手撸 InputStream |
| 鉴权 | 自定义 JWT 拦截器 + `@RequireRole` | **Spring Security** + `JwtAuthenticationFilter` | 身份来源从 `RequestContextHolder` 换成 `SecurityContextHolder`，两者**都是 ThreadLocal，坑一样** |
| Token 位置 | header `token`，拦截器同时支持 URL 参数 | `Authorization: Bearer`，**只认 header** | 后者前端必须用 fetch 而不是 EventSource |
| 角色 | 两级 ADMIN / USER | **三级** USER / MODERATOR / ADMIN | 工具权限分级多一层 |
| 前端 | Vue2 + Element UI（Options API） | **Vue3 + TS + Pinia**（`<script setup>`） | 组件全部重写 |
| 统一返回 | `Result(code,msg,data)` | 同左 | 这两个项目一致 |
| 端口 | 9090 | 8080 | — |

**可以这样收尾**：

> 两个项目我都做了一遍，所以我很清楚这套东西真正难的不是调 API，而是
> 「换线程之后身份还在不在」和「流式协议里那些分片怎么拼」——
> 这两个问题在任何技术栈里都会再遇到一次，换框架只是换个类名。

## 第 5 章 面试问答速查

**Q：你这个和 RAG 有什么区别？**
A：RAG 是检索增强，核心是向量检索——把文档切片向量化、按语义相似度召回。我做的是 function calling，
模型自己决定调哪个工具，工具内部就是原生 MyBatis 查询（SQL `like`）。这个项目里**没有向量库**。
两者解决的问题不同：RAG 解决「模型不知道你的私有知识」，function calling 解决「模型不能操作你的系统」。

**Q：这算真正的 Agent 吗？**
A：取决于定义。如果是「多轮自主规划 + 长期记忆 + 自我反思」，那不算——我是单轮工具调用循环 + 轮次上限。
但如果是「模型自主决策 + 调用外部工具 + 根据结果继续推理」，这是标准 Agent 循环（ReAct 的简化版）。
我刻意没做无限自主：论坛是个多用户系统，可控性比自主性重要。

**Q：模型会不会乱调工具？**
A：会。实测遇到四种：反复调同一个工具（用轮次上限挡）、只说不做（要求执行操作时必须真的调用）、
输出前端渲染不了的 Markdown 表格（提示词约束）、擅自改写用户指定的标题（**这个没根治**，
属于模型行为层面）。所以我不会让 Agent 碰不可逆操作——它只能发帖和置顶，置顶完全可逆，删帖这类不可逆的没开放。

**Q：怎么调试 Agent？**
A：两张审计表。`ai_chat_log` 记每次提问的问答、工具轮次、token、耗时；
`ai_tool_call_log` 记每次工具调用的入参、返回、成功与否、耗时。出问题直接查库就能回答
「它查了什么、看到了什么、花了多少」——Agent 的调试难点在于行为不确定，没有 trace 就是黑盒。

**Q：token 消耗？**
A：实测单次只读问答约 2400-2700 输入、120-180 输出；写操作多一轮工具调用约 4500 输入。
工具返回做了 4000 字符截断，检索结果只回摘要不回正文，不然上下文会被撑爆。

**Q：为什么用 SSE 不用 WebSocket？**
A：SSE 是单向的（服务端→浏览器），正好匹配「模型一直吐字、前端只负责显示」的场景。
WebSocket 是双向的，为这个场景引入连接管理、心跳、重连属于过度设计。另一层：`SseEmitter` 是 Spring MVC 自带，零新依赖。

**Q：为什么前端不用 EventSource？**
A：原生 `EventSource` 只能发 GET、**不能设置请求头**，而本项目的 token 在 `Authorization` 头里。
所以用 `fetch` + `ReadableStream` 手动读流、按 `\n\n` 切事件块。好处是 token 不会进 access log。

**Q：Java 17 和 Java 8 做这个有区别吗？**
A：有。Java 17 能直接用 `HttpClient` + `BodyHandlers.ofLines()`，响应体以行流增量返回，
不用自己管 `BufferedReader` 和关闭；Java 8 项目就只能退回 `HttpURLConnection` 手撸 `InputStream` 逐行读。

**动手练（按难度）**：

1. **加一个只读工具**：查某个用户发过的所有帖子（用 `AiQueryMapper` 加一条 SQL）。
   *验证*：问「lzt 发过哪些帖子」，查 `ai_tool_call_log` 有没有新记录。
2. **把权限再分一级**：新增一个 `ADMIN` 专属工具（比如「任命版主」），
   复用 `ToolPermission` 枚举加一个常量即可。*验证*：MODERATOR 看不到它。
3. **接入项目已有的 Markdown 渲染**：聊天框现在只做最小渲染，
   项目里有 `@kangc/v-md-editor`，试试换用 `VMdPreview` 组件渲染回复。
4. **多轮对话**（最难）：让前端把历史消息带上，后端从 `ai_chat_log` 重建 `messages`。
   *提示*：要加一个会话 ID 把多条记录串起来，表结构本身能撑。
