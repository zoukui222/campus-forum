## 一、做了什么

给校园论坛接入一个**工具型（function calling）AI 助手「校园小助手」**：用户用自然语言提问，
模型自行决定调用哪些站内工具、拿真实数据后再作答，全过程 SSE 流式输出。

6 个工具覆盖「查、读、列、统、写、管」：检索帖子 / 读取正文与评论 / 板块列表 / 论坛统计 /
发帖 / 置顶。其中「置顶」是**版主与管理员专属**，用于演示三级角色（USER / MODERATOR / ADMIN）
下的工具权限分级。

## 二、请求链路

```
浏览器 fetch GET /api/ai/chat?message=...
（Authorization: Bearer <token>，与项目既有的鉴权方式一致）
        │
        ▼
① AiAgentController.chat()          ← 还在 Tomcat 请求线程上！
        │  这里必须做完一件事：把身份快照出来（SecurityContextHolder 是 ThreadLocal）
        ▼
② aiAgentExecutor 线程池             ← 换线程了，ThreadLocal 从此失效
        ▼
③ AiAgentService.run()
        │  ★ 立刻在当前线程「重建」SecurityContext（见 3.1，本项目最关键的改动）
        │  写一条 ai_chat_log（RUNNING）拿主键
        │
        └──► for (round = 0; round < 5; round++)
                 │
                 ├─ DeepSeekClient.chatStream(messages, tools)
                 │
                 ├─ 有 tool_calls ？
                 │     ├─ 有 → ToolRegistry.invoke() 执行工具
                 │     │        ├─ 权限校验（声明层已裁剪 + 执行层二次校验）
                 │     │        ├─ 落 ai_tool_call_log
                 │     │        └─ 结果作为 role=tool 消息塞回 messages → 下一轮
                 │     └─ 没有 → 正文流式推给前端，break
                 │
                 └─ 第 5 轮还在调工具 → 去掉 tools 再问一次，逼它作答
        ▼
④ 回填 ai_chat_log，推 done 事件，清理 SecurityContext
```

SSE 事件：`meta` / `tool_call` / `tool_result` / `content` / `done` / `error`。

## 四、关键设计决策（面试重点）

### 3.1 `SecurityContextHolder` 跨线程失效 —— 本项目最关键的一处

`SecurityUtils.getUserId()` 底层是 `SecurityContextHolder`，默认策略 `MODE_THREADLOCAL`，
只在「处理当前 HTTP 请求的那条线程」上有值。Agent 为了流式输出必须换线程，于是：

1. Agent 线程里 `SecurityContextHolder.getContext().getAuthentication()` 返回 **null**；
2. `SecurityUtils.getUserId()` 捕获异常后**抛 `BusinessException(401)`**；
3. 结果：任何调用它的工具、任何被工具间接触发的 service / 切面，全部报「获取登录用户信息失败」。

这个项目里连积分切面（`ScoreAspect`）都写着注释「因为 AOP 是在同一个线程里执行的，
SecurityContextHolder 依然有效」——作者清楚这个前提，而 SSE 恰恰会打破它。

**处理方式（两种，本项目选第二种）**：

- 方式一（显式传参）：把身份物化成 `AgentContext` 传下去，工具内部只用它，不碰 ThreadLocal。
  优点简单直接；缺点**下游 service 无法复用**，凡是内部调 `SecurityUtils` 的现有代码都得改造或绕开。
- 方式二（**本项目采用**）：在 Agent 线程里**重建 SecurityContext**：

```java
UsernamePasswordAuthenticationToken authentication = new UsernamePasswordAuthenticationToken(
        context.getUserId(), null,
        Collections.singletonList(new SimpleGrantedAuthority("ROLE_" + role)));   // 前缀必须是 ROLE_
SecurityContextHolder.getContext().setAuthentication(authentication);
// …执行工具…
finally { SecurityContextHolder.clearContext(); }   // 必须清理：线程池的线程会复用，否则污染下一个请求
```

这样下游代码**完全无感**——`SecurityUtils.getUserId()`、`@RequireAdmin` 切面、`ScoreAspect`
在 Agent 线程里都能正常工作，一行既有代码都不用改。

`AgentContext` 仍然保留，用于**工具声明层的权限裁剪**（决定模型能看到哪些工具）。
两者分工：AgentContext 管「模型能不能看到」，SecurityContext 管「下游能不能取到」。

### 3.2 中文路径导致 `mvn spring-boot:run` 启动失败（真实踩坑）

现象：`mvn spring-boot:run` 报
`无法找到或加载主类 com.zwz.forum.ForumApplication` / `ClassNotFoundException`，
但 `mvn compile` 明明 BUILD SUCCESS、`target/classes/com/zwz/forum/ForumApplication.class` 也存在。

根因：项目路径含中文（`D:\后端项目\校园论坛\...`）。日志里能看到线索：

```
[INFO] skip non existing resourceDirectory D:\�����Ŀ\У԰��̳\...
```

Maven 把中文路径按 GBK 解码，拼出的 classpath 与实际路径对不上，插件 fork 出的 JVM 就找不到主类。

**绕法**：改用 `mvn package` + `java -jar target/forum-1.0-SNAPSHOT.jar` 启动。
jar 包内是内嵌 classpath，不依赖外部路径解析，实测 6 秒启动成功。
（另：`java -jar` 期间不能重新 `package`，jar 文件被进程占用会导致 `repackage` 报
`Unable to rename ... .jar to ... .jar.original`，必须先停服务。）

### 3.3 Java 17 下用 `java.net.http.HttpClient` 读流

```java
HttpResponse<Stream<String>> response = httpClient.send(request, HttpResponse.BodyHandlers.ofLines());
return parseSse(response.body(), listener);   // 响应体以「行流」增量返回，天然适配 SSE 逐行协议
```

`BodyHandlers.ofLines()` 直接给出行流，不用自己管 `BufferedReader` 与关闭。
（对比：Java 8 项目里只能退回 `HttpURLConnection` 手撸 `InputStream` 逐行读。）

### 3.4 流式 function calling 的 `arguments` 是分片到达的

SSE 里 `tool_calls` 按 `index` 下发：第一片带 `id` 与 `function.name`，之后只带
`function.arguments` 的**字符串片段**。必须按 index 聚合、把片段拼起来，拼完才是合法 JSON。

`DeepSeekClient.parseSse()` 用 `Map<Integer, AiToolCall>` + `Map<Integer, StringBuilder>` 聚合。
不聚合就是随机的 JSON 解析失败。

### 3.5 `SseEmitter` 直接发 `String` 会中文乱码

`SseEmitter.event().data(String)` 走 `StringHttpMessageConverter`，默认字符集 **ISO-8859-1**。
必须 `.data(对象, MediaType.APPLICATION_JSON)` 交给 Jackson 输出 UTF-8。

### 3.6 三级角色下的工具权限双重管控

- **声明层**：`ToolRegistry.buildToolSpec(ctx)` 用 `ToolPermission` 枚举裁剪，
  普通用户**看不到** `top_post`（模型根本不知道它存在，避免注定失败的调用）；
- **执行层**：`invoke()` 再校验一次 `permission.allowed(ctx)`，防绕过。

实测：MODERATOR 可用 6 个工具，USER 可用 5 个。

### 3.7 轮次熔断 + 收口兜底

`ai.max-iterations: 5` 硬上限；触顶后**去掉 tools 再请求一次**，逼模型用已有信息作答，
避免用户拿到空白回复。

### 3.8 工具结果截断与独立线程池

- 单次工具结果回灌前截断到 4000 字符（审计表另存 2000 字），否则上下文会被撑爆；
- Agent 独立线程池（核心 4 / 最大 16 / 队列 50 / CallerRunsPolicy），
  SSE 长连接不会吃光 Tomcat 的 Web 线程池拖垮普通接口；
- `spring.mvc.async.request-timeout: 300000`，容器默认 30s 会掐断 SSE 长连接。

### 3.9 模型的行为问题（提示词层面压，但不能根治）

实测遇到三类，都在 system prompt 里加了约束：

| 现象 | 约束方式 | 效果 |
|---|---|---|
| 用户要求置顶，模型只「查看帖子」然后给文字说明，不执行 | 明确「要求执行操作时必须调用工具真正完成，不要只做说明」 | 修复，改为先查证再执行 |
| 输出 Markdown 表格，但聊天框不做表格渲染 | 明确「不要使用 Markdown 表格，改用 - 列表」 | 修复 |
| 回答开头先吐一句英文思考 | 明确「全程使用简体中文，包括第一句话」 | 修复 |
| 擅自改写用户指定的标题（模型改写成了更「论坛体」的标题） | 提示词压制 | **未能根治**，属模型行为层面 |

## 九、已知限制与后续可做

1. **无多轮对话记忆**：每次提问是独立会话，追问「这篇的正文呢」会丢失上文。
2. **无速率限制**：登录用户可无限提问，生产环境需要按用户限流。
3. **聊天框只做最小 Markdown 渲染**：支持粗体与列表，不支持表格/代码块高亮。
   若要完整渲染，项目里已有 `@kangc/v-md-editor`，可换用 `VMdPreview`。
4. **模型不严格遵循指定字段**：实测会改写用户指定的标题。
5. **`spring-boot:run` 在含中文的路径下不可用**（见 3.2），需用 `package` + `java -jar`。
6. **Redis 依赖**：pom 中引入了 `spring-boot-starter-data-redis` 但代码未实际使用，
   在本机 Redis 未启动的情况下应用仍可正常启动（懒连接），后续要么接入缓存要么移除依赖。
